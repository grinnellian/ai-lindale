# Roadmap

## Origin Story

Ainulindale started inside [aistrologer](https://github.com/grinnellian/aistrologer), a side project where the pattern of structured multi-agent collaboration first emerged organically. The realization: the interesting part wasn't the astrology app — it was the *way the agents worked together*. A TPM that creates issues and drives lifecycle. An architect that plans before code is written. A dev that implements in isolation. Enforcement hooks that keep each role in its lane.

The agents were tightly coupled to aistrologer's domain. DX-001 through DX-003 extracted and genericized them into this standalone framework. The name — from Tolkien's creation myth, the Music of the Ainur — reflects the aspiration: independent voices, each with their own part, producing something coherent together.

## Where We Are

**Pre-alpha.** The core trio works: TPM, Architect, Dev. Each has scoped permissions enforced by PreToolUse hooks. The ticket lifecycle state machine (`/autodev`) drives work through review → plan → implement → verify. Downstream adoption works via git submodule with symlinked agents and hooks. In-repo memory replaced auto-memory for security and auditability.

## The Road Ahead

The roadmap is organized by the problems each layer solves, not by timeline. Later layers build on earlier ones, but within a layer the issues are mostly independent.

### Layer 1: Complete the Core

The framework's foundation is functional but has known gaps that affect daily use.

**Domain expertise.** The core trio knows how to plan and build, but not *what* to build. DX-004 (Generic SME) adds a fourth agent type — a domain subject-matter expert generated by the TPM from project context. The SME advises the architect, reviews dev output for domain correctness, and is owned by the downstream project. The current branch (`dx-004-generic-consultant`) has the template and bootstrap procedure; what remains is wiring it into the workloop.

**Project configuration.** Each downstream project needs to customize agent behavior without forking agent definitions. DX-005 (team-config.yml) provides the configuration surface: role overrides, tool scoping adjustments, SME domain hints, and (eventually) workloop configuration.

**Researcher role.** Some tasks require exploration before planning — scanning codebases, reading docs, evaluating libraries. DX-013 (Researcher Agent) fills this gap. It needs read access and `gh` CLI access but no write permissions.

### Layer 2: Trust and Safety

Agents that write code and run commands need hard boundaries. The current enforcement works but has gaps exposed by real usage.

**Permission hardening.** DX-022 proposes replacing broad sandbox mode with explicit allowlists — more granular, more auditable. DX-020 expands the Dev agent's git denylist to prevent accidental force-pushes and branch deletions.

**Credential safety.** DX-026 addresses credential echoing — agents inconsistently handle tokens in tool output. Some Claude Code instances refuse to display keys; others print them verbatim. The framework needs its own guardrails: PreToolUse hooks that block credential-revealing commands, agent prompt instructions about redaction, and pattern-matching on tool output.

**Auth isolation.** DX-016 scopes MCP server access per agent, so the Dev agent can't access the TPM's GitHub issue API and vice versa.

| Issue | Summary |
|-------|---------|
| DX-022 | Replace sandbox with explicit allowlists |
| DX-020 | Expand Dev agent git denylist |
| DX-026 | Guardrail against credential echoing |
| DX-016 | Per-agent auth isolation via MCP server scoping |
| DX-024 | Subagent permission inheritance for research tasks |

### Layer 3: The Pluggable Workloop

This is the big architectural evolution. Today's workloop is hardcoded: TPM → Architect → Dev. EPIC-002 makes it configurable.

**Quality gates.** The workloop becomes a pipeline with insertion points. A project can configure pre-plan gates (threat modeling before design), pre-merge gates (code review before merge), and post-merge gates (doc staleness checks). Gates are SME instantiations — a security reviewer is an SME whose domain is OWASP and whose personality is adversarial.

**Honest antagonism.** The framework should make it easy to add friction and hard to skip it. Quality gates are friction generators by design. "Honing ideas requires friction" — we want the framework to produce honest internal pushback, not rubber stamps.

**Adversarial SMEs.** The SME template (DX-004) needs to support reviewer/auditor personality types: agents whose job is to find problems, not build things. Security reviewer, code quality reviewer, tech writer, accessibility reviewer — all SME instantiations with different domain expertise and an adversarial stance.

|-------|---------|
| EPIC-002 | Pluggable workloop with quality gates and adversarial SMEs |
| DX-023 | Post-merge doc staleness check (first quality gate) |
| DX-004 | SME template must support adversarial instantiation |

### Layer 4: Adoption at Scale

The framework currently targets greenfield projects — start fresh, generate agents, go. Real-world adoption also means brownfield: existing projects with existing code, existing debt, and existing contributors who may not have formal dev training.

**Brownfield adoption.** A different entry point: audit the existing project → generate a standardization plan → incrementally introduce agents. The wickerman-os project (a self-hosted AI platform built by a self-taught developer) is the test case. The "chunnel" strategy: converge from both ends, making lindale ready for brownfield while making the target project ready to receive it.

**Cross-repo audit.** FEAT-002 adds an `/audit-repo` command for structured analysis of external repositories. This supports brownfield evaluation, dependency auditing, and reference analysis. The command needs scoped `gh` CLI access (DX-024) to work.

**Standardization playbooks.** DX-025 templates the phased plan pattern (Foundation → Tests → Security → Code Quality → Infrastructure) that proved effective on wickerman-os. The TPM generates and customizes this for brownfield projects during bootstrap.

**DevContainer sandboxing.** INFRA-002 extracts the devcontainer pattern from wickerman-os — domain-based firewall via tinyproxy, Claude Code integration, dev tools pre-installed. This solves the sandboxing pain point (DX-022) with a clean isolation boundary. INFRA-003 addresses the unsolved problem of getting properly scoped GitHub PATs into dev containers across platforms.

### Layer 5: AFK Orchestration

This is the end-state vision: **conduct the chorus entirely through GitHub, AFK.** The user doesn't need a terminal open or a Claude Code session running. They interact through issues, PR reviews, labels, and reverts — the same control surface as managing any remote team. The agent team is a set of collaborators who happen to not be human.

The whole point of git: if you don't like what the agents did, `git revert` back to the last known good. Agents commit early and often — small, reviewable, revertable units of work, never one giant commit at the end. The issue thread becomes the audit trail. PRs are the review surface. Labels are the readiness gates.

This requires a trigger mechanism (GitHub Actions, webhook, or long-running service) that starts agent work from GitHub events. The current architecture (Claude Code CLI + subagents) is the inner loop; AFK orchestration wraps it in an outer loop.
