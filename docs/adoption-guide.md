# Adoption Guide

How to adopt the Lindalë agent framework in a downstream project.

## Prerequisites

- Git 2.20+
- [Claude Code](https://claude.com/claude-code) CLI installed
- The framework repo: `https://github.com/grinnellian/ai-lindale.git`

## Initial Adoption

Four commands to get started:

```bash
# 1. Add the framework as a git submodule
git submodule add https://github.com/grinnellian/ai-lindale.git .ai-lindale

# 2. Run the install script to create symlinks and scaffold config files
bash .ai-lindale/scripts/install.sh

# 3. Customize the scaffolded files for your project
$EDITOR .claude/team-config.yml
$EDITOR CLAUDE.md

# 4. Commit everything
git add .ai-lindale .claude CLAUDE.md .gitmodules
git commit -m "chore: adopt ai-lindale agent framework"
```

After this, `/architect`, `/tpm`, and `/dev` commands are available in Claude Code.

## Ongoing Sync

When the framework is updated upstream:

```bash
# Pull latest framework
git submodule update --remote .ai-lindale

# Symlinks already point into the submodule — no reinstall needed.
# If new agents or commands were added upstream, re-run install:
bash .ai-lindale/scripts/install.sh

# Commit the submodule pointer update
git add .ai-lindale
git commit -m "chore: update ai-lindale framework"
```

Or use the convenience script:

```bash
bash scripts/sync.sh
```

## File Ownership

| Category | Owner | Sync | Location |
|----------|-------|------|----------|
| Core agents (architect, tpm, dev) | Framework | Symlink into submodule | `.claude/agents/` |
| Core commands | Framework | Symlink into submodule | `.claude/commands/` |
| Domain SME | Project | Auto-generated by TPM on first run | `.claude/agents/` |
| Skills (project-owned) | Project | Not synced; real directories | `.claude/skills/` |
| Skills (framework-shipped) | Framework | Symlink into submodule, if/when the framework ships any | `.claude/skills/` |
| team-config.yml | Project | Scaffolded once, never overwritten | `.claude/` |
| settings.local.json | Project | Manual | `.claude/` |
| CLAUDE.md | Project | Scaffolded once, never overwritten | repo root |
| Linglink README | Framework | Created by install.sh | `.claude/README.md` |
| Framework docs | Framework | Not exposed downstream | `.ai-lindale/docs/` |
| Framework memory | Framework | Not exposed downstream | `.ai-lindale/memory/` |

**Key insight:** The install boundary IS the context boundary. Only files symlinked into `.claude/` are visible to Claude Code at runtime. Framework internals (docs, memory, CLAUDE.md) stay in `.ai-lindale/` and don't bleed into your project's agent context.

## Claiming a Local Override

Any of the framework-managed paths (core agents, matching commands) can be claimed as a project-local override by replacing the symlink with a real file. `install.sh` will detect the regular file on subsequent runs and skip it — preserving your customization.

**How to claim a managed file as a local override:**

```bash
# 1. Break the symlink and replace with your own content
rm .claude/agents/architect.md
cp .ai-lindale/.claude/agents/architect.md .claude/agents/architect.md
# (edit the copy as needed)

# 2. Commit the real file
git add .claude/agents/architect.md
git commit -m "chore: claim architect agent as local override"
```

From now on, `bash .ai-lindale/scripts/install.sh` will print:

```
  skipped .claude/agents/architect.md -- local override present (delete or re-run with --force to re-link)
```

**`--force` flag:** Re-baselines all managed paths to framework symlinks, replacing any local overrides. Use only when you want to discard your customizations and sync back to framework defaults:

```bash
bash .ai-lindale/scripts/install.sh --force
```

**Summary line:** After each run, `install.sh` prints a summary of what it did:

```
Summary: linked: 5, ok: 1, refreshed: 0, skipped: 1, forced: 0
```

- `linked` — new symlink created (path was absent)
- `ok` — already the correct symlink; no-op
- `refreshed` — stale/wrong symlink replaced
- `skipped` — real-file local override present; not touched
- `forced` — local override replaced by symlink (only with `--force`)

## Skills Convention (FEAT-011)

`.claude/skills/<skill-name>/SKILL.md` follows Claude Code's skills convention:
a directory per skill, containing a `SKILL.md` with frontmatter (`name`,
`description`) plus instructions Claude Code reads when the skill applies.

**Skills are project-owned by default.** Unlike core agents and commands,
the framework does not currently ship any skills — the downstreams that
motivated this convention (juno_automation_alpha's `autocommit` and
`mission-design` skills, cortex-tools'/account-migration's shared
`cortex-recall` skill) built project-specific tooling that isn't generic
enough to upstream. Write your own skills directly at
`.claude/skills/<name>/SKILL.md`; they are real files, version-controlled
with your project, and never touched by `install.sh`.

Use `templates/skill.md` (in this repo) as a starting skeleton for the
frontmatter and structure of a new skill.

**If the framework ships a skill in the future:** `install.sh` scaffolds
an empty `.claude/skills/` directory on every run (same as `.claude/agents/`
and `.claude/commands/`), and symlinks any skill directories present at
`.ai-lindale/.claude/skills/<name>/` using the same `link_managed` logic as
commands — new framework skills propagate downstream automatically, and a
project-owned real directory at the same path is left alone (skipped) just
like a local override of a core agent or command.

## Domain SME Generation

The domain SME is automatically generated by the TPM on first activation. The TPM:

1. Reads project context (`CLAUDE.md`, `README.md`, config files)
2. Identifies the project domain
3. Generates `.claude/agents/<name>.md` and `.claude/commands/<name>.md` from the framework's `templates/sme.md`
4. Uses a domain-fitting name (e.g., `/astrologer` for an astrology project)

The generated SME is project-owned — committed to the repo, customizable, and never overwritten by framework updates. You can also set `sme.domain_hint` in `team-config.yml` to guide detection.

## Troubleshooting

**Symlink target not found:**
Run `bash .ai-lindale/scripts/install.sh` after any submodule operation. Ensure `.ai-lindale/` is populated (`git submodule update --init`).

**Agent not loading in Claude Code:**
Verify `.claude/agents/*.md` symlinks resolve: `ls -la .claude/agents/`. Broken symlinks appear in red.

**Merge conflicts on submodule update:**
Only the submodule pointer (`.ai-lindale` entry in `.gitmodules`) should conflict. Accept the upstream version.

**Cloning a project that uses the framework:**
```bash
git clone --recurse-submodules <repo-url>
# or, if already cloned:
git submodule update --init
bash .ai-lindale/scripts/install.sh
```

**install.sh says `skipped` for a managed path:**
This is expected when a real file exists at that path — it's treated as a local override and left untouched. To keep the override, do nothing. To discard it and re-link to the framework default, either delete the file manually (`rm <path>` then re-run `install.sh`) or run `bash .ai-lindale/scripts/install.sh --force` to replace all local overrides at once.

**`GH_TOKEN` overrides `gh auth login`:**
If `GH_TOKEN` is set in your environment (e.g., from a prior dev container session or bashrc), it takes precedence over `gh auth login` — even if the token has insufficient scopes. Symptoms: `gh issue create` returns "Resource not accessible by personal access token" while `gh auth status` shows you're logged in. Fix: `unset GH_TOKEN` or remove it from your shell profile, then restart your terminal. The OAuth token from `gh auth login` (stored in `~/.config/gh/hosts.yml`) has full scopes; limited PATs do not.

## Future: npm Migration Path

When ready, the framework can be published as an npm package. The `postinstall` script does what `install.sh` does — symlinks from `node_modules/ai-lindale/` into `.claude/`. The linglink and ownership model don't change.
