## Scope

Issue #88 harvests three invariants from `catalyst-build/.claude/agents/dev.md` into upstream:
1. Red phase changes **only** test files, and must **run** the tests (observe the failure)
2. Green phase must **not** change test files
3. Docs-only commits are excluded from the red/green cycle

Explicit ACs: (a) upstream `dev.md` TDD section carries the three invariants; (b) no
project-specific catalyst content leaks in. Review also assesses survival through six later
commits that touched `dev.md`, machine-checkability of the invariants, and internal
consistency with DX-027 (commit cadence / review gate) and DX-012 (merge ordering).

## Machine-checkability assessment

Partially real, partially aspirational — and the ticket is honest about this ("a reviewer
**(or future CI check)** can assert red-touches-tests-only from the diff alone"):

- Invariants 1a/1c/1d are stated in a diff-checkable *form* (`git show --name-only`
  against a test-file predicate), and a consumer exists: DX-027's review gate
  (`autodev.md:114`) cross-references DX-037 by name and instructs the TPM to check
  commit history against the strategy before accepting `ready-for-review`.
- However, **no checker ships** — `scripts/` contains `validate-branch-name.sh` and
  `check-file-overlap.sh` (the DX-012 precedent of advisory scripts) but nothing for
  red/green, and **"test file" is never defined** anywhere in the repo (no glob, no
  convention, no `team-config.yml` key). In a language-agnostic framework the predicate
  is the load-bearing part; without it neither a future CI check nor a downstream TPM
  can apply the assertion deterministically (MINOR-1).
- Invariant 1b (run tests, observe failure) is inherently transcript-checkable only, not
  diff-checkable. The ticket never claims otherwise; noted for the record, not a finding.

## Internal consistency

- **DX-027 (landed after DX-037):** the commit-cadence rule ("one meaningful change per
  commit") and the docs-only exclusion reinforce each other; `autodev.md:114`'s
  monolithic-commit-is-a-blocker gate is built directly on DX-037. Consistent — except
  via BUG-006 (see MAJOR-1).
- **DX-012 merge ordering:** rebase-before-merge preserves the red/green commit pair;
  conflict resolution re-runs tests in the dev worktree. No conflict with DX-037.
- **BUG-006 stage-and-return path:** `dev.md:92-98`, `tpm.md` §"Dispatching dev
  subagents", and `memory/patterns.md:128` all specify a **single**
  `.claude/commit-msg.txt` with all changes staged together. A subagent dev therefore
  physically cannot produce the separate red and green commits this contract requires —
  yet DX-027's gate declares the resulting monolithic commit "itself a blocker, not a
  nit." The three documents jointly contradict on the primary autodev execution path
  (MAJOR-1).

## Findings by severity

### Blocker
None.

### Major
- **MAJOR-1 — Red/green contract is unsatisfiable on the BUG-006 subagent path.** The
  stage-and-return finalization pattern (`dev.md:92-98`, `tpm.md`,
  `memory/patterns.md:128`) supports exactly one commit message per dispatch, while
  `dev.md:53-58` requires two commits (red local, then green push-together) and
  `autodev.md:114` (DX-027) rejects monolithic commits at review. Any dev subagent run
  under the BUG-006 workaround either violates DX-037 or is bounced by the DX-027 gate.
  Root cause is the *interaction* with DX-027 (which landed later) — not DX-037's diff
  itself — so it does not block this ticket, but it needs a follow-up: either extend the
  finalization pattern to a commit *sequence* (e.g. `commit-msg-1.txt`/`-2.txt` or a
  red/green marker in the staged plan), or carve out an explicit BUG-006 exception in
  the `autodev.md:114` gate.

### Minor
- **MINOR-1 — "Test file" is undefined.** The predicate every invariant depends on has
  no definition (glob, directory convention, or `templates/team-config.yml` override).
  Downstream projects (the actual consumers — this repo's own "code" is markdown) can't
  mechanically apply red-touches-tests-only without one. Suggest a config key or a
  one-line convention plus an advisory script alongside `validate-branch-name.sh`.
- **MINOR-2 — Green-phase prohibition has no escape hatch.** "Must **not** touch test
  files" is absolute: it forbids fixing a defective red test, adjusting shared
  fixtures/helpers, or the refactor step of red/green/refactor. One sentence ("if the
  test itself was wrong, start a new red commit") would close the loophole where an
  agent silently weakens a test during green.

### Nit
- **NIT-1 — Tension with Development Standards.** `dev.md:63` ("Before committing, run
  the project's test/build commands") reads as tests-must-pass-before-commit; red
  commits fail by design. `dev.md:56` implicitly overrides it, but a clarifying clause
  ("red commits are expected to fail") would remove the ambiguity for a literal-minded
  agent.
- **NIT-2 — Redundant docs-only guidance.** New `dev.md:60` (docs-only excluded from
  red/green) and pre-existing `dev.md:65` ("Changes to `CLAUDE.md` should not trigger CI
  tests") state overlapping policy two bullets apart; could be consolidated into one
  docs-handling rule.
