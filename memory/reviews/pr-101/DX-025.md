## Fidelity to the sme.md / sme-bootstrap.md sibling pattern

High. Naming convention (`X.md` + `X-bootstrap.md`), `#`-comment header block house style,
step shape (detect → gather context → read meta-template → populate → report), the dual-path
framework/downstream template resolution (`.ai-lindale/templates/...`), `{{PLACEHOLDER}}`
convention, and the closing "project-owned — committed to the repo, never overwritten by
framework updates" clause all match. Appropriate divergences: no frontmatter (generates a
doc, not an agent), simpler single-pass detection in Step 1 (the SME's two-pass content
match has no analogue here), and an issue-creation step the SME flow doesn't need.

## Findings by severity

**Blocker:** none.

**Major:** none.

**Minor:**

1. **DX-019 misattributed as the SME-bootstrapping ticket.** `.claude/agents/tpm.md:74`
   (and the d8f11e0 commit message) say "the brownfield counterpart to **DX-019's SME
   bootstrapping (#22)**". DX-019/#22 is the *Project Bootstrap Interview*; SME
   bootstrapping shipped under DX-004 (#31) (`git log --follow templates/sme-bootstrap.md`
   → fc8ee91 "DX-004: Generic SME agent..."). The interface half of the sentence is
   correct and valuable; the label sends a future agent reading this authoritative prompt
   to the wrong ticket. Fix is a few words: "the brownfield counterpart to SME
   bootstrapping (DX-004, #31); DX-019's (#22) future brownfield branch should invoke...".
2. **Manual audit fallback doesn't span all five phases.** Bootstrap Step 2's fallback
   checklist covers tests, CI, lint/format, and security smells — Phases 2, 3, 4(part),
   5(part) — but never looks for Foundation signals (package manifest, build system,
   Makefile/tasks) or documentation gaps, i.e. Phase 1 and the docs half of Phase 5 from
   the ticket's own source plan (BETA2_PLAN). Combined with the (correct) "only include
   what the audit surfaced" rule, a manual-fallback run structurally produces an empty
   Foundation phase because nobody looked, and empty-is-valid then masks the coverage
   hole. Add two bullets to the fallback checklist.
3. **No trigger moment for brownfield detection.** The sibling SME section says "On first
   activation, check..." and is additionally wired into tpm.md's Self-Orientation step 3;
   the DX-025 section opens "If you detect a brownfield signal" with no stated *when*, and
   Self-Orientation doesn't mention it. As written, detection can simply never run — the
   condition is defined but nothing prompts the TPM to evaluate it. Anchor it to first
   activation (or to the DX-019 interview once that lands).

**Nit:**

1. **Priority test passes via the placeholder token.**
   `test_standardization_playbook_has_priorities` greps for `P0`/`P1`/`P2`, all of which
   match as substrings of the single token `{{P0_P1_P2}}` — the test cannot distinguish
   real priority support from the placeholder's name. Consistent with the file's
   grep-based style, but the weakest of the ten assertions.
2. **Priority semantics don't travel with the artifact.** P0/P1/P2 meanings live only in
   the bootstrap procedure; the generated `docs/standardization-playbook.md` — read by
   downstream humans and agents who will never see the bootstrap — carries bare labels.
   A one-line legend in the meta-template (or an instruction to emit one) would fix it.
3. **Only Phase 1 has a descriptive line.** Phases 2–5 are bare tables. The source plan in
   the ticket had a one-line gloss for every phase; either drop the Phase 1 line or give
   each phase one (a single line each is well within the "less is more" budget).
4. **Brownfield-signal definition duplicated.** tpm.md's inline restatement and bootstrap
   Step 1 define the signal independently and could drift — the same
   restate-vs-pointer pattern flagged in the FEAT-013 review. tpm.md could carry just the
   trigger and point at Step 1 for the definition.
5. **Heading case.** `## Brownfield adoption` (sentence case) sits among Title Case
   siblings in adoption-guide.md ("Claiming a Local Override", "Engagement Handoff",
   "Future: npm Migration Path").

Non-findings checked and cleared: the "empty phase is valid" language appearing three
times in ~140 template lines is redundancy-as-emphasis for a prompt-following consumer,
not padding — accepted as intentional; the Status checklist listing all five phases even
when a phase may be empty is harmless (an empty phase is trivially complete); Step 4
saying "replace all placeholders" while Issue is "filled in during Step 5" is
self-acknowledged sequencing, not a contradiction; `.ai-lindale/templates/...` downstream
path resolves via the submodule layout (whole repo checked out — no per-file install step
needed for templates); no test asserts the empty-phase/less-is-more resolution, but no AC
demanded one.

## Verdict rationale

Every proposal bullet is delivered, the contested design question was resolved the right
way and — the specific thing this review was asked to confirm — the "less is more"
resolution is *enforced in the template's own language*, not just decided: the skeleton
ships one placeholder row per phase, forbids invented boilerplate at both generation
sites, and teaches the TPM to report empty phases as success. Pattern fidelity to the SME
sibling is high, both cross-ticket interfaces (DX-019, FEAT-002) are defined without
scope creep, tests are red-first and green. The three minors are real but small and
mechanical to fix (a mislabeled ticket reference, two missing audit-checklist bullets, a
missing trigger anchor); none undermine the shipped design. **APPROVE-WITH-NITS**.
