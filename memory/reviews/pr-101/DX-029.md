## Summary

The mechanical core is clean and correct: `maxTurns` is a real, documented Claude Code
subagent frontmatter key (re-verified against code.claude.com/docs/en/sub-agents this
session), and all five live agent definitions carry the expected tiers at branch tip —
audit-repo 30, researcher 40, architect 50, tpm 100, dev 200. The researcher (created
after DX-029 landed, in c26629e) slots coherently into the scheme, and the CLAUDE.md
Retry/Loop-Detection reference is now accurate rather than forward-looking. But two of
the ticket's four ACs are not demonstrably met, and neither shortfall is recorded
anywhere: AC3's "graceful exit with summary" is contradicted by the official docs
("Maximum number of agentic turns before the subagent stops" — a stop, with no
summary semantics), and the ticket's own defaults table assigns SME 30, yet
`templates/sme.md` gained no `maxTurns` and `templates/sme-bootstrap.md` never
instructs the TPM to set one — so generated SME agents remain uncapped, the exact
runaway class this ticket exists to close. The orchestrator's issue comment claims
implementation "per this ticket's suggested scheme" with no caveat. The fixes are
small (one template line, a decisions.md entry, an AC waiver note on #47), which is
why this is REQUEST-CHANGES rather than anything heavier.

## Findings by Severity

### Blocker
None.

### Major

1. **AC3 silently dropped — no graceful-exit behavior exists and no waiver was
   recorded.** The docs describe a hard stop at the turn cap; the agent gets no
   opportunity to emit "what was accomplished and what remains." That may well be
   unimplementable from frontmatter alone (agents cannot count their own turns, and
   the harness owns the cutoff), which is a legitimate reason to narrow scope — but
   scope narrowing must leave a paper trail. The orchestrator's comment on #47
   ("Implemented ... per this ticket's suggested scheme") reads as full satisfaction.
   Requested change: comment on #47 recording the platform limitation, amend or
   explicitly waive AC3 (and note AC4's verification status), and mirror that in
   `memory/decisions.md`. Closing #47 as-is would check off an AC that is not met.

### Minor

1. **`templates/sme.md` has no `maxTurns`, and the omission is nowhere recorded as
   deliberate.** The ticket's defaults table explicitly lists SME 30. The commit
   message even leans on that row ("audit-repo=30 ... same tier as SME per ticket
   rationale") while leaving the SME template itself uncapped. `templates/sme-bootstrap.md`
   (all 90 lines checked) never instructs the TPM to set `maxTurns` when generating,
   so every downstream-generated SME ships without runaway protection. Requested
   change: add `maxTurns: 30` to the sme.md frontmatter block (or a bootstrap step
   setting it). Note in passing: sme.md still carries `permissionMode: plan`, a field
   the DX-013 commit message calls pre-EPIC-004 and dropped elsewhere — adjacent
   drift, not DX-029's fault, but worth a follow-up ticket.

2. **Tier values and rationale are not documented in-repo (AC2's second clause).**
   The scheme's reasoning exists only in the commit message and the GitHub issue.
   `memory/decisions.md` — the repo's declared landing zone for new decisions per
   CLAUDE.md ("New architectural decisions land in memory/decisions.md first") — has
   no DX-029 entry. An agent calibrating a new role's cap (as DX-013's author had to
   do for researcher) must archaeology the git log. A short decisions.md entry with
   the five values and the "read-heavy < planning < orchestration < implementation"
   ordering rationale satisfies AC2 properly.

3. **AC4 is asserted, not verified.** No test or recorded experiment demonstrates
   that an `Agent()`-spawned subagent is actually cut off at its role's cap. Test
   coverage exists only for researcher, and `scripts/tests/test-researcher-fixtures.sh:128`
   asserts mere presence (`maxTurns:`), not the tier value 40 — the other four agents'
   caps have no test at all, so a future edit could silently drop or re-tier them.

4. **Main-session applicability is unknown for this repo's primary launch mode.**
   CLAUDE.md's documented workflow is `claude --agent tpm`; the docs list `maxTurns`
   in the *subagent* frontmatter reference and (unlike `initialPrompt`, whose entry
   explicitly addresses main-session behavior) say nothing about whether it caps a
   main interactive session. Runaway protection may therefore only exist for
   dispatched subagents, not the operator-facing TPM session. Worth a one-line
   verification or caveat wherever AC2's documentation lands.

### Nit

1. **Field-order inconsistency in dev.md.** Four files append `maxTurns` after
   `initialPrompt`; `dev.md:20` inserts it between `color` and `initialPrompt`.
   Cosmetic, but the DX-036 review showed these frontmatter blocks get diffed and
   merged repeatedly — uniform ordering keeps those diffs boring.

2. **Researcher fixture test under-asserts.** `test_agent_has_max_turns` would pass
   on `maxTurns: 999999`. Asserting `maxTurns: 40` costs nothing and pins the tier.

## Specific Assessments Requested

**Is `maxTurns` a real frontmatter key?** Yes — re-verified this session.
https://docs.claude.com/en/docs/claude-code/sub-agents 301-redirects to
https://code.claude.com/docs/en/sub-agents, whose "Supported frontmatter fields"
table includes `maxTurns` ("Maximum number of agentic turns before the subagent
stops"), and the `--agents` JSON flag documentation lists it among accepted fields.
The implementer's verification claim on #47 is corroborated.

**Tier-scheme coherence (architect 50, audit-repo 30, researcher 40, tpm 100,
dev 200):** Coherent. It matches the ticket's table exactly for the four roles the
table names (SME→30 mapped onto audit-repo, with the mapping reasoned in the commit
message), and the two post-hoc roles interpolate sensibly: audit-repo at the
read-heavy SME tier, researcher at 40 — above audit-repo (WebSearch/WebFetch
round-trips cost turns) and below architect (still read-only, no dispatch). The
ordering read-only-analysis < planning < orchestration < implementation is internally
consistent. The values remain uncalibrated guesses, which the ticket itself
anticipates ("calibrate from experience") — acceptable, but that is one more reason
they belong in decisions.md where calibration updates can be recorded (Minor-2).

**CLAUDE.md Retry/Loop-Detection reference accuracy:** Accurate at branch tip.
CLAUDE.md:132 — "`maxTurns` (DX-029) provides a hard ceiling, but agents should
self-regulate well before hitting it." Notably, `git log -S maxTurns -- CLAUDE.md`
shows this line landed in 0cefb94 (2026-03-22), months *before* the implementation —
it was a forward reference to an open ticket that 719a9b1 has now made true. "Hard
ceiling" is also the honest framing (vs. the ticket's "graceful exit"), so CLAUDE.md
needs no edit; the discrepancy to resolve is on the ticket side (Major-1).

**Should templates/sme.md carry maxTurns; was the omission deliberate?** It should
(`maxTurns: 30`, the ticket's own row), and I found no evidence the omission was
deliberate: not mentioned in the commit message (which cites the SME row for a
different purpose), not in the orchestrator's #47 comment, not in sme-bootstrap.md,
not in memory. Treated as an oversight — Minor-1.
