### Minor

**m1 — Audit misses the commands-as-skills registration point (`autodev`, `handoff`, `pr-refresh`).**
The implementation's framing — "this repo ships no skills of its own" (repeated in every
agent file's Skills section and the adoption guide) — is only true of `.claude/skills/`.
Under Claude Code's merged model, `.claude/commands/*.md` files *are* project skills, and
this repo ships eight: five role invocations (correctly excluded per AC-5) plus three
genuine capabilities — `autodev` (ticket lifecycle), `handoff` (engagement wrap-up
checklist; tpm.md's own body tells the TPM to follow `/handoff`), and `pr-refresh` (PR
queue reconciliation). The issue explicitly says "The audit should check `.claude/skills/`
and any other skill registration points." None of the three are mentioned, even to say
"considered and deliberately not preloaded." Impact is low — per the sub-agents docs,
subagents can still invoke unlisted project skills through the Skill tool, so nothing is
lost at runtime — but AC-1's "audit **all** available skills" is incomplete as documented.
Fix: one sentence in the adoption-guide section (and optionally tpm.md) addressing the
three non-role commands, e.g. "not preloaded because they are operator-initiated
workflows the TPM reads on demand."

**m2 — audit-repo's no-skills rationale over-generalizes and is factually wrong for several skills.**
`.claude/agents/audit-repo.md` claims the twelve bundled skills "all either build, run, or
diff a local checkout." That is true of `run`, `verify`, `run-skill-generator`,
`code-review`, `simplify`, `batch`, and `design-sync`, but false for `claude-api` (pure
API reference material — touches no checkout), `loop` (re-runs a prompt on an interval —
no repo involvement at all), `dataviz` (chart design guidance), `debug` (reads the session
debug log), and `fewer-permission-prompts` (edits `.claude/settings.json` — which
contradicts the role's read-only constraint, but not via a "local checkout"). The
*conclusion* (assign none) remains defensible skill-by-skill — those five are irrelevant
to or in conflict with an API-only external-repo auditor for other reasons — but the
stated blanket reason is inaccurate, and this section is exactly the rationale AC-4 asks
for. Fix: split the sentence ("most build/run/diff a local checkout, which this role never
has; the rest are irrelevant to gh-api-only repo analysis or conflict with read-only").

**m3 — No runtime confirmation that bundled skills are actually preloadable via `skills:`.**
The docs' `skills:` examples all show project skills; the field's documented failure mode
for a missing/disabled skill is a *silent skip with a debug-log warning*, and skills with
`disable-model-invocation: true` cannot be preloaded at all. Nothing on the branch (test,
commit message, or docs note) shows an agent launched with `--agent dev` and the preloaded
simplify/claude-api/verify content confirmed in context. If bundled-skill preloading
silently no-ops, the ticket's whole deliverable degrades to documentation. Probability is
low (bundled skills are model-invocable, so they sit in the preloadable set) and the
degradation is graceful, but the repo's own "chfirm" principle (`dd3383f`) would ask for
one observed run. Fix: a one-time manual chfirm noted in the ticket, or a follow-up test
once such verification is scriptable.

### Nits

**n1 — `test_no_role_invocation_as_skill` uses a fixed `grep -A5` window and a hardcoded role list.**
`scripts/tests/test-skills-assignment.sh` line 119: a skills list longer than five entries
would let tail entries escape the check, and the alternation `(architect|dev|tpm|researcher|audit-repo)`
must be manually extended when a new role agent lands. Deriving role names from
`.claude/agents/*.md` basenames and using `awk` over the frontmatter block would make the
guard future-proof.

**n2 — Fixture assertions grep the whole file, not the frontmatter block.**
`assert_file_contains "$DEV_FILE" '  - simplify'` (and siblings) would still pass if the
entry migrated out of the frontmatter into body text, and `'^skills:'` would match a
markdown line starting with `skills:` anywhere in the file. Harmless today (verified the
current files have no such collisions) but the tests assert weaker properties than their
names claim. Scoping the grep to the `--- ... ---` block would close it.

**n3 — Architect's "read-only as long as `--fix` is never passed" is prompt-enforced only.**
With hook enforcement retired (EPIC-004), nothing hard-blocks `/code-review --fix`.
Mitigating: the architect's tool list has no `Write`/`Edit`, so the fix-application path
has no tools to execute with — the constraint is defense-in-depth-by-omission rather than
by rule. Worth one clause in the rationale ("and the role's toolset cannot apply fixes
anyway") so the safety argument doesn't rest on the prompt alone.
