## Findings

### Blockers
None.

### Major
None.

### Minor

1. **Human-detection heuristic is underspecified against its own signature convention.**
   `autodev.md:93-94` defines a human response as a comment "not signed by an agent role
   (no `-Claude <Role>` signature)". The agent constraints (tpm.md, architect.md) require
   the signature "as the exact final line of the comment" — but the protocol text doesn't
   anchor to that, so a naive containment reading misfires both ways:
   - *Human quoting an agent:* a human reply that block-quotes the escalation comment
     (including its `-Claude TPM` line) "contains" a signature and would be misclassified
     as agent → missed resume. Fail-safe direction (ticket just stays escalated), but a
     silent stall.
   - *Agent unsigned by mistake:* an agent comment missing its signature is classified as
     human → false resume and premature label flip. Fail-unsafe direction. Mitigated by
     the MUST-sign constraints, but the protocol should say the signature test is
     "final line", not mere presence.
   Note the heuristic can't fall back to comment author: agents post through the
   operator's own `gh` auth, so human and agent comments share a login. That rationale is
   sound but unstated — worth one sentence so a future editor doesn't "fix" it to
   author-based detection.

2. **Repeat-escalation ambiguity.** `autodev.md:92-93` scans for comments "after the
   TPM's own escalation comment". A ticket escalated, resumed, and re-escalated has
   multiple `## Needs Human` comments; the protocol should say "the latest escalation
   comment" (and that its Resume-as field wins over stale tracker entries, or vice versa
   — currently the tracker is only a fallback "if the comment isn't available/legible",
   which is fine, but only if "the comment" is pinned to the latest one).

3. **AC5 (adoption guide) unaddressed and downstream label provisioning is a gap.**
   Neither the adoption guide nor `scripts/install.sh` creates or documents the
   `needs-human` GitHub label for downstream repos — labels don't travel with git, so a
   downstream `/autodev` run following this protocol will fail label application until
   someone creates it manually. This gap pre-exists for *all* lifecycle labels
   (`needs-arch-review`, `arch-approved`, etc.), so it isn't introduced by DX-030 — but
   DX-030's AC is the only one that explicitly names the adoption guide, and no
   "not applicable" ruling was recorded. Suggest: a one-line label-bootstrap note (or
   `gh label create` snippet) in the adoption guide, or an issue comment recording why
   it's out of scope.

4. **README escalation section is now stale relative to this protocol.**
   `README.md:82-88` ("Escalation Protocol (User AFK)") still describes the pre-DX-030
   flow: every blocker gets the `blocked` label, no `needs-human`, no structured comment,
   no resume protocol. The later doc sweep (`9672c16`) didn't touch it. Current-state
   coherence issue, not part of this ticket's diff — but it's the public-facing document
   contradicting the authoritative one.

### Nits

5. **Template field name reuses the vocabulary the protocol just distinguished.** The
   opening paragraph (`autodev.md:59-63`) is at pains to separate `needs-human` from
   `blocked`, then the escalation-comment template's first field is `**Blocked at:**`
   (`autodev.md:79`). "Escalated at:" or "Paused at:" would keep the vocabulary clean.

6. **Dangling flow name in Rules.** Rules line 111 (added by DX-011) says the
   blocked-first summary "mirrors the resume-first flow in the Escalation Protocol" —
   but the protocol section never names or describes a "resume-first flow" (it specifies
   a per-run resume *check*, with no stated ordering relative to other work). The
   cross-reference points at something that doesn't exist under that name.

7. **Mechanical resume vs. human intent.** Resume steps 1-3 (`autodev.md:95-99`) apply
   the pre-recorded Resume-as label regardless of what the human actually said (e.g.
   "don't proceed, close this"). In practice the TPM reads the comment, and Rules line
   116 (DX-028 fold-in, which explicitly lists "escalation resume" as a checkpoint —
   good cross-wiring) partially covers it, but one clause like "unless the human's reply
   changes the disposition" would close the letter-of-the-protocol gap.

8. **Label cosmetics.** The `needs-human` GitHub label color (`#FBCA04`) is identical to
   `in-progress` (`#fbca04`), so the two most attention-asymmetric states are visually
   indistinguishable in the issue list; and the `blocked` label's description ("Blocked
   on external dependency **or decision**") blurs exactly the decision-goes-to-
   `needs-human` line the protocol draws. Label metadata, not repo content — noting for
   whoever owns label hygiene.
