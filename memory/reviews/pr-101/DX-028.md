## Design assessment

- **TPM-only integration is the right call and correctly framed.** Folding description edits
  under the existing "Only TPM creates GitHub issues" exclusive authority (tpm.md:42-43) extends
  an established invariant instead of inventing a parallel one. autodev.md's rule places the fold
  *before* advancing state, which is the correct ordering — the next agent dispatched reads the
  description post-fold.
- **Checkpoint list verified against the CURRENT autodev.md state machine.** All three enumerated
  checkpoints map to real comment-reading points: "arch review completion" → NEEDS_REVIEW row
  (planner posts TDD plan comment; TPM applies `arch-approved` on completion, autodev.md:50);
  "ready-for-review" → REVIEW row (autodev.md:53); "escalation resume" → ESCALATED row plus the
  DX-030 Resuming procedure, which explicitly fetches comments via `gh issue view N --json
  comments` (autodev.md:91-99). No enumerated checkpoint is phantom. One real comment-reading
  point is missing from the enumeration — see minor M2.
- **No conflict with DX-038.** DX-038's memory tracker is scoped to "TPM-internal state that
  doesn't map to a GitHub label" (autodev.md:12-13); DX-028 governs the ticket *spec*. The two
  authoritative-source claims partition cleanly (process state vs. spec content) and neither text
  contradicts the other. The DX-038 review of this branch (memory/reviews/pr-101/DX-038.md:43-44)
  independently called the DX-028 rule orthogonal; concur.
- **No-changelog requirement honored exactly.** Both tpm.md:58 and decisions.md:163-165 state
  that GitHub edit history is the audit trail and forbid "Update N" notes in the body — matching
  the ticket's explicit instruction rather than gold-plating an extra audit mechanism.

## Findings by severity

### Blocker

None.

### Major

- **M1 — AC-3 unmet: the flagging half of the protocol is invisible to the agents who must
  perform it.** tpm.md:56 and decisions.md:157-158 assign architect and dev a duty: when their
  comment changes scope or design, "they say so explicitly in the comment (e.g. 'this changes the
  AC — description should be updated')". But that instruction lives only in `tpm.md` (loaded into
  TPM sessions) and `autodev.md` (a TPM command) — neither is ever loaded into an architect or
  dev session, and `.claude/agents/architect.md` / `.claude/agents/dev.md` were not touched by
  `a7aeeec` and contain nothing about flagging or the description-is-spec convention. The
  cross-role trigger the ticket's "Open Design Questions" explicitly asked to be designed is
  therefore answered on paper but not wired. Mitigation exists — tpm.md:57 has TPM independently
  check for unfolded decisions at every checkpoint regardless of flags — so the system degrades
  gracefully rather than breaking, which is why this is major rather than blocker. Fix is small:
  add a two-to-three-line note to architect.md and dev.md (e.g. under their issue-comment
  conventions) stating the description is the spec, they must not edit it, and scope/design-
  changing comments must carry an explicit "description should be updated" flag for TPM.

### Minor

- **M2 — Checkpoint enumeration presented as exhaustive omits triage.** tpm.md:57 frames the
  parenthetical as complete: "At *every* point TPM reads a ticket's comments during the state
  machine (arch review completion, ready-for-review, escalation resume)". The OPEN/triage row
  (autodev.md:49, "validate ACs are clear and scoped") is also a point where TPM plausibly reads
  an existing comment thread — tickets carried across sessions or re-triaged after discussion —
  and triage is precisely where an unfolded thread decision would corrupt the "validate ACs"
  judgment. autodev.md:116's generic phrasing ("any checkpoint where comments were just read")
  covers triage implicitly, but its parenthetical repeats only the three. Either add triage to
  both lists or reword tpm.md:57 so the list reads as examples rather than an exhaustive set.
- **M3 — The protocol is not yet dogfooded on its own ticket.** Issue #43's description still
  presents the three "Open Design Questions" as open, though this implementation resolved all
  three (answers live in tpm.md and decisions.md). Per the very protocol being landed, TPM should
  fold the resolved answers into the #43 description at the ready-for-review checkpoint before
  advancing/closing. Not a defect in the branch content (description edits are TPM-exclusive and
  this reviewer is read-only on GitHub) — recording it here so the TPM run that processes PR #101
  performs the fold and the ticket closes consistent with its own rule.

### Nit

- **N1 — Heading level contradicts the stated placement.** The new tpm.md section is `###` (line
  52), a *sibling* of `### EXCLUSIVE AUTHORITY: Issue Management` (line 42), whose existing child
  is `#### Issue Numbering Protocol` (line 45). Yet the section text says "as part of the
  Exclusive Issue Management authority **above**", and decisions.md:166-167 and the commit
  message both say it is "under Exclusive Authority: Issue Management". To match the stated
  structure it should be `#### Issue Description as Authoritative Spec (DX-028)`; as written, the
  prose claim and the document outline disagree.
- **N2 — "Reads a ticket's comments" is slightly imprecise for the ready-for-review checkpoint.**
  At the REVIEW state the scope/design discussion typically lives in *PR review* comments
  (autodev.md:53), not issue comments, while the fold target is the issue description. The intent
  (fold decisions wherever they surfaced into the issue body) is clear from context, but a
  parenthetical in tpm.md:57 — e.g. "(including PR review threads at ready-for-review)" — would
  remove the ambiguity about what TPM is expected to scan at that checkpoint.

## Summary

The protocol core is well-designed: TPM-only integration is correctly derived from existing
exclusive issue-management authority, the checkpoint hooks match the real state machine, the
no-changelog requirement is honored exactly, and the decisions.md entry is one of the better ones
in the file. But AC-3 is unmet — the cross-role flagging duty the protocol itself defines is
written only where architect and dev will never see it — and under this repo's "satisfied" review
bar that requires changes: a small addition to `architect.md` and `dev.md`, plus the M2/N1/N2
wording fixes, would bring this to approval.
